Zako — Architektura porównawcza: Monolit vs Mikroserwisy

Dokument zawiera komplet diagramów obu wariantów wdrożenia aplikacji Zako (rezerwacja biletów kolejowych): wersji monolitycznej (Spring Boot na pojedynczej bazie Postgres) oraz wersji mikroserwisowej (auth + trip + ticket + Kafka).

5. Sekwencja — zakup biletu

5.1 Monolit (jedna transakcja)

sequenceDiagram autonumber participant U as Uzytkownik participant M as Monolith :9090 participant DB as ticket_monolith_db U->>M: POST /api/tickets/purchase Bearer JWT M->>M: JwtAuthFilter, load User Note over M,DB: BEGIN M->>DB: SELECT trip WHERE id M->>DB: SELECT from_station, to_station M->>M: check availableSeats > 0 M->>DB: UPDATE trips SET available_seats = available_seats - 1 M->>DB: INSERT INTO tickets Note over M,DB: COMMIT M-->>U: 201 TicketResponse

5.2 Mikroserwisy (REST + Kafka, eventual consistency)

sequenceDiagram autonumber participant U as Uzytkownik participant T as ticket-service participant TS as trip-service participant DBK as ticket_db participant K as Kafka participant DBT as trip_db U->>T: POST /api/tickets/purchase Bearer JWT T->>T: JwtAuthFilter, userId z claim T->>TS: GET /api/trips/id TS-->>T: TripDto T->>T: check availableSeats > 0 T->>TS: GET /api/stations/from and /to TS-->>T: StationDto x2 T->>DBK: INSERT INTO tickets DBK-->>T: ticket.id T->>K: publish ticket.purchased T-->>U: 201 TicketResponse Note over K,DBT: asynchronicznie K->>TS: consume ticket.purchased TS->>DBT: UPDATE trips SET available_seats = available_seats - 1

5.3 Anulowanie biletu (mikroserwisy)

sequenceDiagram autonumber participant U as Uzytkownik participant T as ticket-service participant DBK as ticket_db participant K as Kafka participant TS as trip-service participant DBT as trip_db U->>T: POST /api/tickets/id/cancel T->>DBK: SELECT ticket T->>T: assert owner and ACTIVE T->>DBK: UPDATE status=CANCELLED T->>K: publish ticket.cancelled T-->>U: 200 K->>TS: consume ticket.cancelled TS->>DBT: UPDATE trips SET available_seats = available_seats + 1

9. Wybrane decyzje projektowe

  1. Denormalizacja stacji + czasow w tickets (mikroserwisy). Bilet po sprzedazy nie zalezy od pozniejszych zmian w trip_db.
  2. Identyfikatory bez FK miedzy bazami. Ticket trzyma user_id, trip_id, station_id jako liczby; weryfikacja przez REST przy zakupie.
  3. Kafka KRaft single-node zamiast klastra z ZooKeeperem — wystarczajace dla demo.
  4. CORS — monolit uzywal setAllowedOrigins("http://localhost:4200"); zmienione na setAllowedOriginPatterns dla localhost:* i ingress hostow.
  5. spring-boot-flyway starter w ticket-service — flyway-core sam z siebie nie aktywuje autoconfig w Spring Boot 4.0, migracja V1 byla pomijana.
